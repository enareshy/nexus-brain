# Build plan (phases, tasks, exit criteria)

Durations are estimates for 4–6 engineers; with Claude Code they are the human-review cadence, not coding time.

## Phase 0 — Foundations (3–4 wks)  [FR-ID-01..03, NFR-DX-01, NFR-OBS]
Tasks
1. Scaffold pnpm + Turborepo monorepo per TECH-STACK layout; TS strict, ESLint, Prettier, Vitest, husky + gitleaks.
2. `docker-compose.yml` local infra (see file); `pnpm infra:up`, health script.

4. `packages/db`: Drizzle schema, migrations, RLS policies, `withTenant(tx, tenantId)` helper, seed (2 tenants, overlapping people).

6. `packages/telemetry`: OTel tracing, pino logger with context.
7. `packages/evals`: skeleton harness + 30-query seed golden set; CI workflow runs typecheck/lint/test.
Exit criteria
- Login works; JWT → tenant/user context; RLS isolation tests pass (tenant A cannot read B).
- `pnpm dev` runs api+web shell; CI green; eval harness executes on seed set.

The model sees only the question and has no tools, and its output is cut down to plain words before use. If it fails, search continues as asked. Failures were seen but not explained: 3 of about 15 calls in the running API failed with a connection error, then 0 of 9 after that, and 2 of 235 recorded calls failed with no retry in one run and 0 of 235 in the next. It retries once, and logs the network error code to catch the cause next time. Limit: 30 a minute per user, counting repeats, cached 5 minutes. `pnpm eval` replays recorded real output (`golden/rewrites.json`), so CI needs no key; re-record with `scripts/record-rewrites.ts` if the questions or prompt change, and a partly failed run writes nothing. Measured 2026-11-01 on the same synthetic set, rewriting every question as the answer path does: recall@10 0.82 to 0.97, nDCG@10 0.81 to 0.87, paraphrase recall 0.00 to 0.85. Costs of it: a rephrased question that is found often ranks low (paraphrase MRR 0.35); multi-source ranking drops (MRR 1.00 to 0.87), and exact titles and keyword questions slightly (to 0.98 and 0.96); no-answer questions returning results rise from 20 to 21 of 40. Known gaps: the search bar never rewrites if one loosely related result matches, which was seen live, so those searches still miss; the search path does not stop the rewrite if the client disconnects; answers wait for the rewrite before searching, and that added time has not been measured; search-bar questions that found nothing, and all answer questions, go to Anthropic. CI requires recall of 0.85 with rewriting.

The shared lock is now asked for every 25 to 200 ms instead of waited on inside Postgres, so a cancelled wait frees its connection at once (no fairness between waiters, which are at most one per connection per server).
- One registration per service (2026-11-08): until Brain has a saved registration with a service, starting a connection to it holds a lock per service, in-process and shared across servers, so two people connecting it for the first time together get one registration rather than one overwriting the other.
- DNS rebinding closed (2026-11-08): every outbound MCP and OAuth request connects through an undici Agent whose look-up resolves the name again and hands the socket only public addresses, so a name that turns private after the first check is refused when connecting (NFR-SEC-05). undici 8.12.3 was already in the workspace (installed offline) and is now a direct dependency of `@brain/mcp-client` for this. Requests passed as `Request` objects are refused on this path; the MCP SDK passes URLs. A loopback name allowed for local testing must also resolve only to loopback; connections are capped at 20 per service; Teredo, 100::/64 and the local NAT64 range are blocked too. Remaining gaps: no egress proxy support (a proxy would need the address check moved to the proxy's target); the allow-list is by host name, not port.
- Shared connection lock built (2026-11-07): all work on one person's connection to a service (searches, reads, writes, connect and disconnect) now holds a Postgres advisory lock as well as the in-process one, so two API servers cannot refresh one rotating token at once and sign the person out of that service. The lock is held on its own pool of connections (20 per server), so waiting for it cannot starve the work; a wait over 8 s, or no free lock connection, reports the service as busy. Postgres drops the lock if the server holding it loses its connection, within about a minute even if that server died without closing it (TCP keepalives on the lock pool); in that rare case another server may start before the first finishes. Remaining gaps: the lock pool size is fixed at 20 per server (more connections in use at once wait up to 5 s, then report busy); losing the lock part-way is not logged; a write or read callback must never use the same connection again inside the lock, or it waits on itself.

Search still runs every time, which is what re-checks access. Checked live: asking the same question twice cost one answer.
Turning people off built (FR-CON-02 offboarding, FR-ADM-01): a People page where an admin turns someone off or back on. In one database transaction the person loses sign-in to the web app and to Brain's MCP server, their automatic agents pause, running agents are cancelled, changes waiting for their approval are rejected, and their stored tokens are deleted and then revoked at each provider that supports it. Database triggers refuse anything new for them, including from work already in flight, and the scheduler skips them. Only an active admin may act, never on themselves, and only an owner on an owner; both people are locked and re-checked inside the transaction. History is kept; turning someone back on restores sign-in only, so they reconnect services and turn automatic agents on again. Approving a change takes the same lock, so an approval and a turn-off happen one after the other. Gaps: no SCIM (FR-ID-04), so removing someone from the identity provider does not turn them off in Brain; a change already approved and being carried out still finishes, and the admin is told how many; revocation at the provider happens once, right after the change, so if the API stops at that moment or the provider fails, the grant is not revoked (our copy of the tokens is already gone); any admin may turn back on someone an owner turned off, unless they are an owner; refused attempts are logged but not added to the audit trail.
Prompt caching built (FR-LLM-05): agent turns cache the instructions and tools, which every run shares, and each run's conversation as it grows, with the five-minute lifetime. Checked live with `apps/api/scripts/cache-check.ts` (a few cents; re-run it after changing how agent requests are built): each turn reads everything the previous turn sent, a second run reads the shared part, and two three-turn runs cost 36% less; longer runs save more. Answers and search words are not cached, because their instructions are shorter than the 512-token minimum and everything after them changes on every request, so a cache write would only add cost. Cached prompts are matched byte for byte and return nothing themselves, so nothing passes between people.
Phase 3 remaining: a second provider for failover (FR-LLM-02, FR-LLM-04), suggested as Claude on AWS Bedrock, which needs an AWS account; people choosing their own tier (FR-LLM-03). The answer cache and breaker are per server process.

Status
Memory built (FR-AST-07): a Memory page where a person adds, edits and deletes things Brain should remember about them (up to 30 lines of 300 characters). Only text the person types there becomes a memory: no document, tool result or model output can create one, so planted text cannot make itself permanent. Memories are private to the person (row-level security, no admin view), sealed at rest, and never written to the audit trail, which records only that one changed. They are read fresh for every answer and every agent turn and never stored with a conversation or run, so deleting one takes effect from the next request; tests check this for answers, for an agent mid-run, and against a damaged row. An answer that used memories is never put in or served from the shared answer cache. The model is told memories are private and must not be copied into anything written for others. Checked live: a memory saying "answer in French" changed a real answer, and the next answer after deleting it was in English. Gaps: answers already given, conversation history and agent results may still mention a deleted memory; Brain does not suggest memories itself; skills, summaries and @Brain mentions are still to come.
Budgets and usage dashboard built (FR-MET-03, FR-MET-04 in part): a Usage page where admins see this month's AI cost for the company, by feature, person and day, and set a monthly limit for the company and one for each person, with a warning level. The limit is checked before every answer (including the paid rewording of the question), before an agent starts and before each agent step; automatic agents skip and say so once a day; a run whose budget check cannot run stops rather than spend blindly. Everyone sees a banner as their limit nears; members see only whether the company's limit is nearly or fully used, never how much it has spent. Calls with no known price count as $0.50 each so they cannot slip past a limit. Changes to limits are audited with the old and new values. Months are calendar months in UTC. Checked live: a $0 limit stopped a real answer and agent before any call, and removing it restored them. Gaps: calls already running when a limit is reached still finish, for everyone in the company, so a limit can be overshot by those calls (reserving money before each call would close this); plans with pooled credits and top-ups (FR-MET-02, FR-MET-04) need pricing decisions; reconciling the ledger with the provider's invoices needs its admin billing access.
Summaries built (FR-AST-06, in part): each search result has a Summarise button. Brain reads that one item again with the person's own access and writes a few cited bullet points, through the same path as answers, so it shares their rate limit, budget, metering, memories and permission-safe cache. Summaries are audited by item, never by content, and not saved to chat history. A read that stalls or that the person leaves stops after at most 20 seconds, so it cannot hold one of their answer slots. Slack results offer no summary, as Brain cannot read a Slack message in full. Gaps: a summary that fails for a passing reason says it could not read the item, the same as for no access; not yet checked live, because the local test accounts' real connections were removed (see below).
@Brain mentions built (FR-AST-05, Jira comments only): a new kind of automatic agent, "When I write @Brain in a Jira comment". Every 5 minutes it finds issues with recent comments containing "Brain" and reads their comments with the person's own connection. Only comments the person wrote themselves, never edited by anyone else, from the last day, count; the text after "@Brain" becomes the start of a run's goal, made one plain line of at most 1,000 characters, followed by the person's standing instructions. Each comment starts one run; mentions already there when the agent is added are ignored; the usual limits apply (one such agent per person, 3 runs per check, 10 automatic runs a day); every change still waits for approval. Everything Brain writes to Jira (comments, summaries, descriptions) has "@Brain" turned into "Brain", so its own text, posted as the person, can never start another run. Mentions inside code blocks or quoted lines are ignored, and only the paragraph the mention starts is taken, so pasted material after it is left out. A comment with no editor recorded never counts. Issues are read one at a time, at most 10 per site per check, so other people's "Brain" comments cannot cause a burst of calls. Gaps (security review, 2026-11-03): the comment and account shapes are not yet checked against live Jira (needs a reconnected Atlassian account); on a busy account, more than 10 recently commented issues means some mentions are missed, and a very long thread may not return its newest comments; rendered @-mentions of other people inside the request are passed on as text; a timed-out check is not cancelled; seen-event rows are never purged; comments in Confluence and other services are not read; a request edited after it was picked up is not run again. The connections integration test (simulated Jira) failed once in four full runs; not investigated.
Drafts and subtasks built (FR-AST-06, now complete): each search result Brain can read also offers Draft… and, for a Jira issue, Suggest subtasks. Both read the item again with the person's own access and go through the same path as summaries, sharing their rate limit, budget, concurrency slot, metering and audit, which records the item but never the draft request or any text. A draft is what the person asks for in their own words (one plain line of at most 500 characters), written from the item with citations; on a Jira issue a finished draft can be sent for approval as a comment, without its citation markers. Suggested subtasks come back as at most 8 plain titles of at most 200 characters, parsed on the server from the model's list and never shown as free text; the person ticks the ones they want, and each becomes its own `create_subtask` proposal under that issue. Nothing reaches Jira until each is approved on the Changes page. The target site, parent issue and issue type never come from the model: the site and parent are the result the person picked, and the subtask type is looked up from the parent's project on a site the person can write to. Sending several carries on past a failure, names what was not sent, and trying again sends only those, so nothing is proposed twice. A refused or cut-short suggestion says so rather than showing an empty list. Gaps: agents cannot yet propose subtasks themselves; the project lookup searches by key and reads the first 50 matches, so on a site with very many similarly named projects it may wrongly say subtasks cannot be added; not checked against live Jira (the `parent` argument and subtask type shape follow the tool's description).

Skills built (FR-AST-08): a Skills page where a person saves named instructions (up to 4,000 characters and 60 lines) with a choice of the agent's tools, and can share one with their company. The owner alone can change or delete a skill; colleagues can use a shared one, another company never sees it (row-level security, with tests), and a turned-off person's skills are no longer offered. Names and instructions are sealed at rest and never written to the audit trail, which records only which skill changed. When starting an agent, a person can pick a skill and is shown its full text and tools first. The run copies the skill at that moment, so a later edit or deletion cannot change a run already going; a skill edited after the person opened it is refused ("read it again") rather than followed unseen. The run is offered only the skill's tools, and any other tool call is refused without running. A colleague's skill is framed to the agent as a way of working, not permission: do only what the person's goal needs, and never put information into a proposal because the skill says so; every change still needs the person's approval. Skill text cannot hide anything: invisible and look-alike-blank characters are refused, runs of blank lines and tabs are collapsed, and its tags are escaped. Gaps: automatic agents cannot use skills yet; a run does not show afterwards which skill it used (the audit has its id); admins cannot remove a colleague's shared skill; the skill rule is in each run's first message rather than the agent's system prompt, so the recorded agent eval (which a prompt change would invalidate, at about $2 to re-run) still applies.

Plans, credits and reconciliation built (FR-MET-02, FR-MET-04): each company can have a plan with a monthly pool of credits, where one credit is one cent of AI cost. The plans (Pilot 5,000, Team 20,000, Business 100,000 credits a month) are placeholders in `packages/core/src/plans.ts` until pricing is decided. An operator sets a company's plan with `pnpm --filter @brain/db set-plan <tenant-id> <plan> [credits]`, which needs the owner role; the app can only read plans (tests prove a company cannot raise its own). Agent work, started by a person or automatically, uses credits and pauses when they run out, checked before a run starts and before every step; answers, summaries, drafts and search wording never use credits, even on a fallback model, but still count toward the spending limits. A company with no plan works as before. Admins add top-ups on the Usage page; they count for the calendar month (UTC) they are added in, are audited, and can never be changed or removed. The Usage page shows credits left, the plan, and this month's top-ups; everyone sees a banner when credits are nearly or fully used, saying that answers still work, and never how much was spent. When a spending limit and credits are both used up, the spending limit is named, as adding credits would not help. `pnpm --filter @brain/db reconcile <YYYY-MM> <bill.csv>` compares a month of the usage ledger, for all companies, with the provider's bill (`model,cost_usd` lines prepared from the provider's cost report) and fails unless the total and every model are within 3%; it prints totals only and needs a role that can read every company's ledger. Gaps: no payment, so a top-up is a record, not a purchase; unused credits do not roll over; the bill must be prepared by hand, as the provider's cost report format and the Admin API are not wired in; the 3% exit criterion has not been checked against a real bill.

Work graph built (FR-RET-09, per person, 2026-11-08): the project owner chose a graph for each person rather than one for the whole company, since Brain stores no documents and a shared graph could show someone that a document exists. Each person's graph (migration 0026, `work_graph_edges`, readable only by them under RLS) holds only service and item ids, never titles or text: items they opened (a summary, draft or subtask suggestion that read the item), sources of answers they rated up, and those sources linked to each other. Their own search results, for search and for answers, are then reordered: a linked result is lifted by up to half its rank score (`packages/connectors/src/work-graph.ts`), so it moves up a few places but never past much better matches, and nothing is ever added or removed. Links fade by half every 30 days, are dropped after 90, count repeats up to 20, and are capped at 5,000 per person. A rating down teaches nothing, and rating the same answer up again does not count twice. A problem with the graph never fails a search or rating, and a search waits at most 250 ms for it; results then keep their search order. Ids with control characters are not stored. The graph is in the person's data export, and erasing a person removes it (a trigger added in 0026, which also removes their rate-limit rows, missed by 0025; it runs with the caller's rights, so only the erase itself, as the data keeper, reaches the person's rows). `pnpm test:leak` now includes the end-to-end graph test (one person's ratings never change another's order). Measured with `pnpm eval` on 164 questions derived from the synthetic set (each question cut to two keywords, asked once with the right answer in the history and once with another matching result): MRR 0.791 without the graph and 0.810 with it; 0.831 when the history matches, 0.789 when it does not. A stronger lift (1.0) scored 0.945 and 0.706, better only if at least about a third of histories match, which real use has not shown yet, so the safer setting is used. The documents are invented, so this shows the mechanism and its cost, not real gains; lifting an answer the person used is bound to help, so the part of the gate that can fail is the cost when the history is unrelated, which must stay at or under 0.02 MRR (the 1.0 setting would fail it). The eval rebuilds the links in TypeScript rather than through the database, so the SQL is covered by integration tests instead. Gaps: clicking a search result is not recorded (only reads through Brain are); old links are only removed when the person next uses Brain, so someone who stops keeps theirs until erased (a periodic sweep would fix it); pruning runs on every write; the stronger setting should be revisited with real feedback, together with the learned ranker (FR-RET-08).

Seeing and clearing your own work graph (FR-RET-09, 2026-11-10): the Memory page has a section, "What Brain learned from what you use", listing each item by service and id (titles are never stored) with how it was used and when, newest first (up to 200; the export has everything). The person can forget one item (every link to or from it) or clear it all after a confirmation; both are audited with counts only. The routes are `GET /me/work-graph`, `POST /me/work-graph/forget` and `DELETE /me/work-graph`, always the signed-in person's own, with no admin route. Checked in the browser against the local stack.

Learned ranker built (FR-RET-08, offline first, 2026-11-08): the project owner chose one ranker per company, learned from everyone's ratings there with no record of who rated. The first time an answer is rated, each of its results is saved as general signals only: its place in the search's own order (before any personal reordering, so the ranker never learns from itself), match score relative to the best, age in whole days, and which service, with whether it was cited in an answer rated up (useful) or was one of the others in it (not); an answer rated down teaches only that its cited results were not. Each answer is saved once, under a keyed hash of company and message, so changing a rating, retrying or rating twice at once adds nothing (migration 0027, `ranking_examples`: no person, id, title or text, saved by day not time; the app can add rows and see only which answers are saved, never their signals). An operator trains every company's ranker with `pnpm --filter @brain/api ranker:train` (owner role, no model calls): a small logistic regression over those four signals and a weight per service, every weight bounded to plus or minus 3 (`packages/connectors/src/learned-ranker.ts`). It needs 150 rated answers, trains on four in five, and is switched on only if, on at least 30 held-back answers, it ranks the cited result higher than the search's order did by at least 0.02 MRR; otherwise ranking stays as it is. Ratings older than 180 days are deleted when training runs. Searches and answers then apply the company's model before the person's own work graph; the model is cached for 10 minutes and read once for searches arriving together, a search waits at most 250 ms to read it, and after a slow or failed read searches keep their order for 30 seconds. Measured with `pnpm eval` by offline replay on the synthetic set (made-up ratings from four questions in five, scored on the fifth): only 147 rated answers come out, too few to train, so the eval does not exercise switching it on, and held-back MRR is unchanged at 0.791; unit and integration tests show it learns, switches on when ratings hold a pattern, stays off without one, and leaves another company unaffected. So the requirement's acceptance (a measured gain) is not met yet: it needs real ratings. Ratings saved for the ranker hold no person, so they are not in a person's export or erased with them (their effect stays in the company's model until it is retrained); deleting the company deletes them. Gaps: training is manual (no schedule yet), so old ratings are only deleted when it runs; there is no admin view of whether the ranker is on; a company with few people is effectively learning from those few; a member could still skew it with many genuine-looking ratings, bounded by the weight limit and the held-back check.

Test hygiene: integration and leak tests now run against their own database, named after the dev database with `_test` added (`brain_test` locally; `TEST_DATABASE_URL` and `TEST_DATABASE_APP_ROLE_URL` override it). A global setup creates it when missing, each suite migrates and seeds it, and any database name not ending in `_test` is refused, so the tests can no longer remove real connections from the dev database, and they can run while the local API is up. The turn-off tests also create and remove their own temporary people.

Status
Data retention, export and company delete built (FR-ADM-03, NFR-COMP-01 in part): a Data page for everyone. Each person can download everything Brain holds for them as one JSON file: profile, chats with their messages, memories, skills they wrote, agent runs with their steps, automatic agents, proposed changes, and which services are connected (never tokens or anything of a colleague's). It is audited without content, refused if it cannot be audited, allowed once a minute per server, and marked if it ever had to leave runs or changes out. Admins set how many days the company keeps chats (from their last use) and finished agent runs with their notifications; shortening asks first, stating what will go. An hourly sweep removes what has expired, in rounds until done, through one database function owned by a role of its own that can only read ids and dates and delete those rows, like the agent scheduler's; one company's failure does not undo the others, sweeps never overlap, runs still working or waiting for a decision are never removed, and each company's removals are audited as counts. An operator deletes a whole company with `pnpm --filter @brain/db delete-tenant <id> "<exact name>"`, which needs the owner role and refuses until everyone is turned off (which revokes their connections at each service), locking them meanwhile. Gaps: retention covers only chats, agent runs and notifications, not proposed changes, memories, skills, automatic agents or usage records, and the audit trail is append-only by design; the export leaves out usage records, notifications and audit entries about the person; deleting a company removes only this database, not sign-in accounts at the identity provider or copies anywhere else, and its own audit trail goes with it, so the operator's output is the record; the export includes text Brain read from connected services in agent steps, which the person could already read.
Erasing one person built (FR-ADM-03, GDPR right to erasure): on the People page an admin can erase someone already turned off, after a confirmation that says it cannot be undone. Everything they own is deleted in one transaction: chats, memories, skills (including ones shared with others), agent runs, automatic agents, proposed changes, notifications, group memberships and any connection left; their name, email and sign-in identity are replaced with placeholders, so they can never sign in or be turned back on. The usage costs and audit trail the company must keep stay, under an anonymous id, and nothing new can be written for them, even by a chat already under way. It is done by a database function, owned by the same narrow role as the retention sweep, that checks everything itself under a lock: only the signed-in active admin may erase, only an owner may erase an owner, nobody erases themselves, and nobody whose approved change is still being carried out. Gaps: audit entries keep the person's id, now pointing to the placeholder; colleagues' agent runs that followed one of their shared skills keep the copy of its instructions they started with; their sign-in account at the identity provider must be removed there; anything copied out of Brain, such as Jira comments it posted for them, is outside it.
Admin console built (FR-ADM-02, FR-LLM-07 in part): an Admin page where admins set the company's AI settings and reach everything else they look after (People, allowed services on Connections, Usage and credits, Data, Activity). The settings are the model answers and agents use (most capable, or balanced at about half the cost; search wording always uses the fast model), whether people can use agents, whether automatic agents run, and how many automatic runs each person may have a day (1 to 10, never above the built-in 10). Everyone can see the settings; only an active admin can change them, checked again in the database, and each change is audited with the old and new values. They are kept per company with row-level security, with tests. They are read before every answer, summary and draft, before an agent starts and before every agent step, so a change applies at once: turning agents off refuses new runs and stops a run already going before its next step, even a tool call saved before a restart; a run whose settings cannot be read stops rather than carry on unchecked. Automatic agents skip quietly while turned off, without reading any service, and the Agents page tells people when agents are off. On the balanced model, answers do not use refusal fallbacks, so a fallback can never pick a model the company did not choose, and cached answers are never shared between models. Gaps: a model call already under way when agents are turned off still finishes and is billed; a schedule that falls due while automatic agents are off waits for its next time, and @Brain comments written meanwhile may run once they are back on if under a day old; an answer fails if the settings cannot be read; only two models can be chosen, and there is no region pinning (FR-LLM-07) or per-tool agent policy (FR-AGT-04 always/never/ask), as every change already needs approval and destructive tools stay disabled; the model eval and the recorded agent eval cover only the most capable model.
Answers when the AI is down (NFR-AVAIL-01, in part): if the AI service is down, overloaded or paused by the circuit breaker before an answer has started, the answer ends with the search results the person was already sent and a note saying the AI is not available and to try again in a minute, instead of an error. In chat the panel lists every result found, linked only when the address is safe; on the Search page the results are already shown below. The answer is saved to the chat as search results only and left out of the history the model sees later, and the audit trail records why the AI was unavailable (such as provider_503 or circuit_open), as well as any usage the provider may have billed. A wrong API key or model name is not treated as an outage, so it still shows as an error and gets fixed. An answer cut off part-way, or one the person cancelled, still reports the failure as before. Gaps: summaries, drafts and subtask suggestions still report an error, as they have nothing to show without the AI; agents stop with "AI service could not be reached"; with AI not configured at all, answers still say so before searching; the 99.9% availability target needs production monitoring, so it is not measured; not checked in the browser, as the only local account with a source connected reads a real Jira site.
Undo for Jira edits built (FR-WR-06): before an approved change to an issue's summary or description is sent, Brain reads those fields as they are, in Jira's own document format so formatting survives, and saves them; once the change succeeds it reads them again. If that first read fails, nothing is sent and the approval stays open. On the Changes page a finished edit offers "Undo", which proposes setting the fields back: it is an ordinary change the person must approve, shown in full, and only one can be waiting or done for each change. When it is approved, Brain checks the fields still hold exactly what its change left; if anyone edited them since, it sends nothing and says so, rather than overwrite their work. An undo can itself be undone the same way. The saved fields are kept with the change, only its owner can see or undo it (row-level security), the app cannot alter which change an undo targets or the state it expects (column grants, with a test), and they are included in the person's data export. Gaps: new issues, subtasks and comments cannot be undone, because that would need delete tools, which stay disabled; agents cannot propose an undo; the saved fields are not sealed at rest, like the change's own arguments, and are not covered by retention; if reading the fields back after a change fails, that change cannot be undone; the Jira read and compare have been tested against a simulated Jira only, as no Atlassian account is connected locally; the agent run view does not offer undo; the check is best-effort, as Jira cannot compare-and-set: an edit someone makes in the moment between Brain's change and its read-back, or between the undo's check and its write, can be overwritten; Jira may reformat a description between reads, which makes an undo refuse safely though nothing changed (code review, 2026-11-06). Tightened afterwards: the database saves what an undo would put back once, while the change is sent and after it succeeds, and refuses to let a new change start with it or any later update replace or clear it, from any role short of dropping the trigger (migration 0024, with a test); and undo requests are checked under the same per-person lock as other changes, so several at once give one undo and one audit entry.
